# 001: Self-hosted extractor tier for URL transcription

**Date**: 2026-09-14
**Status**: Accepted
**Gates**: #181 (server extraction strategy), #182 (strategy override + connectivity status)

## Context

The URL transcription router (`src/transcription/url-transcription.ts`) has two tiers: YouTube captions over HTTP on every platform, and yt-dlp/ffmpeg extraction on desktop. Mobile has no `child_process`, so TikTok, Instagram, and captionless YouTube videos cannot be transcribed on a mobile-only setup; the current answer is to leave the intake note un-stamped for a synced desktop vault to finish. Closing that gap needs media extraction to run somewhere other than the phone. Two locked constraints stand in the way: the plugin ships no runtime npm dependencies, and media tooling runs only as local external processes on desktop. A third tier that calls an HTTP extraction service adds a network client, a bearer key, and a trust boundary to infrastructure the plugin does not control. That combination has to be a recorded decision, not an implementation detail.

## Decision

Add a third tier, `ServerExtractionStrategy`, that POSTs a media URL to a **user-operated, self-hosted** extraction service and hands the returned audio to `AudioModule.transcribe`. The service lives in its own repository as a container image bundling yt-dlp and ffmpeg. The plugin bundles nothing new: local extraction keeps using `execFile` on desktop, and the new tier uses `requestUrl`, the same HTTP client every provider call already uses. Self-hosted wins over the alternatives on the plugin's own terms. A bundled WASM extractor was rejected in the 2026-03-19 log entry (no URL fetching, ~25 MB, unverified in mobile WebViews). A project-operated service would make the maintainer a relay for user URLs and copyrighted media, with a hosted cost and outage surface. Third-party download APIs sit outside the user's control and their terms shift. With self-hosting, URLs go only to a machine the user runs, the same posture the plugin takes with Ollama. The tier is opt-in: `canHandle` returns true only when `video.serverEndpoint` is set. The endpoint must be `https://` unless it is a loopback or private-range address, because the plugin will send a bearer token to it. The key is stored as `video.serverApiKey`, exactly like the existing provider keys: plain `data.json`, gitignored, scrubbed by `redactSecrets` at every log and notice sink, rendered through the shared credential field with a "Test" button backed by `GET /healthz`. The response is validated at the edge and trusted nowhere else. A `200` must carry an audio content type and a non-empty body under the size cap. `X-Media-Title` and `X-Media-Duration` are optional, length-limited strings; a malformed duration is dropped, not fatal. Error responses must be JSON `{ code, error }` and map to typed errors (401 invalid key, 400 unsupported URL, 413/422 over cap, 502 extractor failure, network or timeout unreachable) with upstream text redacted before it reaches the user. `UrlTranscript.source` gains `'server-extraction'`. Tier order is fixed at **captions → local → server**. Captions are free and instant. Local extraction is free and keeps media on the user's machine. The server tier costs the user bandwidth and compute, so it runs only when the cheaper tiers decline; on a desktop with yt-dlp installed it is never reached unless the #182 override forces it.

## Consequence

Mobile gains TikTok, Instagram, and captionless-video transcription when the user runs the service; without an endpoint, behavior is unchanged and the desktop-sync handoff remains the documented fallback. Time-range clipping, local video download to the vault, and dependency checks for yt-dlp/ffmpeg paths stay desktop-only; the server tier does not write a video file into the vault and reports no `videoVaultPath`. The service contract (`POST /v1/extract`, `GET /healthz`, header names, error codes) becomes a versioned boundary that both repositories must keep in step, and any change to it needs a new ADR that supersedes this one. The plugin takes on a small, typed HTTP client and a settings section, tested with mocked responses only; no live service is exercised in CI. The security posture is that of every provider key already in settings, plus one new rule: the endpoint field is a URL the plugin will send a bearer token to, so it is validated on save and the key is never sent to a non-loopback `http://` address. `docs/adr/` is established by this record as the home for decisions that cross a locked constraint; the dated log in `DECISIONS.md` continues to carry the full history.
